# Design Decisions Registry

Every design question that affects production, and its state. **Open items
must not be decided in code.** Implementation that depends on an open item is
blocked (`[!]`) until the developer records a decision here.

- **OPEN**: undecided; do not invent an answer.
- **DECIDED**: locked by the developer. The source is noted.
- **PROPOSED**: a production recommendation from the audit, awaiting approval.

## Decided

| ID | Decision | Source |
|---|---|---|
| D-01 | Wrikshagandha is a peaceful exploration/life game; farming is one part of a larger living world, not the core identity | Master production direction |
| D-02 | Core loop: explore → discover → collect → return → tend → unlock → world changes → explore again | Master production direction |
| D-03 | The world is organized around five elemental experiences, each eventually a gameplay system (environment, interactions, mechanic, wildlife, discoveries, progression, secrets, atmosphere, world-state changes), not just a biome | Master production direction |
| D-04 | **Element themes.** Earth/Prithvi: soil, plants, farming, forests, physical life, stability. Water/Jala: ponds, rivers, flow, aquatic life, reflection, healing, water discoveries. Fire/Agni: warmth, transformation, cooking, craft, sacred fire, transformation of materials. Air/Vayu: wind, movement, sound, birds, height, freedom. Space/Akasha: silence, mystery, ancient knowledge, stars, hidden places, deep exploration | Master production direction |
| D-05 | The current Meadow/Garden is the first Earth prototype; elements are prototyped one at a time in the order Earth, Water, Fire, Air, Space | Master production direction |
| D-06 | Conceptual relationship: **Element = what the world expresses; Rishi = wisdom/understanding associated with that element.** Nothing beyond this is decided | Master production direction |
| D-07 | Two movement modes, Tap-to-Move and Joystick, on one shared movement system | Master production direction |
| D-08 | Tap-to-interact (touch the object itself) is the interaction direction; no permanent Interact button | Master production direction |
| D-09 | Interaction verbs are generic capabilities: Inspect, Collect, Harvest, Talk, Open, Enter, Exit, Use, Give, Plant, Water, Feed, Read. No crop/discovery/NPC-specific hacks in player or input code | Master production direction |
| D-10 | Coins are an internal reward system. **1000 coins = ₹10** is a long-term *reference* for a separate future redemption backend only: configuration/business logic, never gameplay logic. No real-money redemption, payments or crypto now | Master production direction |
| D-11 | Farming feature expansion is frozen; farming will be integrated with inventory, economy, saving, exploration, NPC requests and progression; FarmManager to be reduced so inventory/economy don't live in it *(M06.5: integration through Phase 06 done and the boundary frozen — ARCHITECTURE §8, checker "farming frozen".)* | Master production direction |
| D-12 | Small vertical slice first (meadow, garden, pond, forest edge, path, simple house, simple NPC, wildlife, discoveries, basic elemental prototype, farming, inventory, coins, journal, saving); no large world expansion before the Vertical Slice Gate | Master production direction |
| D-13 | Placeholder art until the gameplay architecture is proven; final art/world building is a dedicated later phase | Master production direction |
| D-14 | Crop count stays at 4 (no more crops before the farming loop is proven fun) | Developer instruction (farm depth milestone) |
| D-15 | **The world itself is the control.** Tap ground → walk there; tap an object → walk to it and interact. Taps work in both movement modes. The movement-mode setting only chooses whether the joystick is shown. Joystick/keyboard input always takes over from a tap-started walk; a new tap replaces the current target. Refines D-07 | Developer instruction (touch interaction fix) |
| D-16 | Interaction range for tapped objects is the existing player interaction range (the InteractionZone), not a separate reach: the player walks toward the object and interacts once it's in range. No per-object distances. Resolves O-08 | Developer instruction (touch interaction fix) |
| D-17 | **Save versioning (was P-01).** The save file carries a top-level integer `save_version` (1 since M04.0; absent = 0 = written before M04.0). A load migrates older saves one step at a time (one step per version in `SaveManager._migrate()`); refuses a save from a newer build and never overwrites it that session; treats a version that isn't a whole number ≥ 0 like a corrupted file; passes a section to its system only if its JSON type is the expected one (else that section's default). **Rule:** any change to what is saved (new section, renamed or reshaped field) bumps `SAVE_VERSION` and adds its step — the bump is what stops an older build from silently dropping newer data. `farm.version` stays as FarmManager's own (unused) field | Developer instruction (M04.0) |
| D-18 | **Quality is an attribute of held produce, not an item identity (was O-13).** One produce item per crop; the ItemStore keeps one count per quality level (`ItemDefinition.quality_levels`, produce = FarmManager's Plain / Good / Fine). Quality is decided at ripening and only scales points and size; everywhere the player sees produce it is one crop with a quality split | M04.2 audit recommendation, implemented on the developer's instruction (M04.2) |
| D-19 | **The player's items have one owner: the `Inventory` autoload (was O-14).** It holds the one `ItemStore` (never handed out) and is saved as `items`. FarmManager changes it only through its seed/basket rules; Inventory gives **one collectible per discovery collection, first or repeat** — an `ItemDefinition` with category `collectible` and that `discovery_id` (named as the discovery); a discovery without one gives nothing. Items have no value or use yet; caps on repeat rewards belong to Phase 05 (A4) | Developer instruction (M04.3) |
| D-20 | **Coins live in a `Wallet` autoload, separate from Wriksha Points.** Points stay the score (`PointsManager`); coins are the future buying/selling currency (D-10). The Wallet's **append-only ledger is the truth**: every change is one `{amount, reason}` entry, the balance is their sum and never negative, and only the ledger is saved. Only `credit`/`debit` change it. No coin earn/spend exists yet: M05.3's earn rules turned out to be points only, and M06.2 (after O-01) is where legitimate coin earning/spending may be introduced; how points and coins relate: closed by D-24 (independent). *(M06.2: O-01 closed by D-25 — coins are earned only by selling produce, `Market.sell()` the one `credit` caller; no debit.)* | Developer instruction (M05.1) |
| D-21 | **Exploration rewards are once ever (was P-02).** Places reached, secret places found, the "every secret found" bonus and the curiosity bonus are saved (`exploration` section) and pay once ever; a load restores them without paying or announcing anything, and a malformed saved bonus flag counts as paid. Deliberately left repeatable/session-scoped: discovery collection (points + collectible every time, M04.3), the daily bonus (once per day), the discovery-count thresholds (bounded by first-ever discoveries) and session beats. Caps/diminishing returns on repeatable rewards are rates → with the earn rules (M05.3, O-01) | Developer instruction (M05.2) |
| D-22 | **Reward amounts are data; never-respawning discoveries are once-ever.** Flat Wriksha Points rewards are `RewardRule`s in `data/rewards/` (points only; per-definition amounts stay on discoveries/crops; the harvest quality scale stays FarmManager's rule, D-11). Repeat collection of respawning discoveries stays unlimited (no caps/diminishing returns — O-01 open; *D-25 closed O-01 without caps by keeping coins off every such source*). A discovery with `respawn_seconds <= 0` (the Ancient Seed) is claimed by its first collection — the saved `discovered_ids` is the record, no new save field — so it never spawns, pays or becomes the daily target again. Respawn timers are still not saved; no daily anti-clock logic (offline design) | Developer instruction (M05.3: D1 a, D2 b, D3 keep, D4 points only, D5 keep) |
| D-23 | **Economy configuration is data read by no gameplay code.** `EconomyConfig` (`data/economy/economy_config.tres`) holds D-10's redemption reference exactly — 1000 coins = 10 INR (`redemption_reference_coins`, `_amount`, `_currency`) — for a future backend/redemption phase; nothing in scripts, scenes or UI reads or shows it, and it is not wired to the Wallet or to points. FarmManager's `QUALITY_POINT_SCALE [0.75, 1.0, 1.5]` stays in FarmManager as a frozen farm-quality rule (not an economy rate). Crop `points_value` keeps also setting crop display order (documented, unchanged). `RewardRule`s stay separate in `data/rewards/` | Developer instruction (M05.4: E1 keep, E2 reference only, E3 keep, E4 separate) |
| D-24 | **Wriksha Points and coins are permanently independent (closes O-02).** Points stay the progression/achievement score (`PointsManager`), earned by all the existing reward sources, saved and shown exactly as before; coins stay the Wallet's future gameplay currency with no current sources or sinks (balance 0 until a later milestone adds legitimate coin rewards — *that milestone is M06.2: selling produce, D-25*). Points are never converted to or from coins and never mirrored into them; no reward pays both; no rate exists (`EconomyConfig`'s 1000 coins = ₹10 is a redemption reference only, D-23). Of O-02's documented options this is "keep both" | Developer instruction (M05.5) |
| D-25 | **The coin economy: coins are earned only by selling produce (closes O-01).** Harvest → produce enters the Inventory → the player sells it (Basket screen, confirm first) → the Wallet receives coins. **Sources:** only `Market.sell(item_id, quality, quantity) -> int` — the `Market` autoload is the one caller of `Wallet.credit()`. Harvest itself pays **no** coins (points and produce exactly as before); discoveries (first or repeat), the daily discovery, landmarks, secrets, curiosity, discovery thresholds, farm milestones, collectibles, seeds and Wriksha Points pay **no** coins. **Sellable:** only items with `category == "produce"` and `sell_value >= 1` (`ItemDefinition.sell_value`, 0 = unsellable); seeds and collectibles never sell. **Prices (locked, independent of `points_value`):** base `sell_value` wild_carrot 5, meadow_herb 6, golden_sunflower 8, elderbloom 12 (the Good price); quality percents (`SellRules`, `data/market/sell_rules.tres`) Plain 80 / Good 100 / Fine 140 — a coin rule of its own, never `QUALITY_POINT_SCALE`; `unit = (sell_value × percent + 50) div 100` (whole numbers, half up, per unit), `total = unit × quantity` — so carrot 4/5/7, herb 5/6/8, sunflower 6/8/11, elderbloom 10/12/17, and 3 Fine carrots = 21. **Sale:** validate (item, produce, sell_value, quality, quantity ≥ 1, held) → price (≥ 1) → remove the items → credit once → if the credit is refused, put the exact items back → `produce_sold`; **one ledger entry per confirmed sale**, reason exactly `sell:<item_id>:<quality>` (no price, text or time). GameState saves on `produce_sold`, so items and wallet are saved together; the Market never saves. **No sinks** in M06.2 (no `debit` caller: no seeds, plots, services, cosmetics, trade, gifts or redemption for coins). No caps or cap state (the only coin faucet is produce that exists). **No retroactive coins** for existing saves; produce already held sells normally. `SAVE_VERSION` stays 5 (no new saved state). Points and coins stay independent (D-24); EconomyConfig stays unread and the D-10 reference outside all gameplay and UI (D-23) — the coin balance is its own "Coins N", never ✿ points, never ₹ | Developer decisions after the M06.1 audit (O-01 A–J; values approved M06.2) |
| D-26 | **Mobile UI language and HUD layout (M06.3).** The UI is designed on the 1080 × 1920 portrait canvas with one shared theme, `scenes/ui/wriksha_theme.tres`, in the existing parchment / bark / leaf palette. Interactive controls on the HUD, Basket and Inventory are **at least 120 canvas px**. The HUD's top bar is **anchored to the top and sized by its content** (never stretched): ✿ points pill, discovery count, then 📚 📖 ⭐ 🕹; notifications below it; **🧺 Basket and 🎒 Inventory bottom-right** in the thumb zone (🧺 still shown only while produce is held); both follow the display's safe area. **Points and coins stay visually separate** — the ✿ points pill vs the amber "Coins N" chip, never one label (D-24). Cards keep one system: the harvest card keeps the care note ("watered with care" / "left thirsty") so the care rule stays learnable; the sale card shows CROP / quality ×qty / +N Coins from the Market's reported values. The Inventory stays read-only. Collection, Journal, Daily and the SeedPicker are deliberately unchanged in M06.3 (a later UI pass). Presentation only: no gameplay, economy or save change | Developer decisions (M06.3 audit: numbering, care note kept, other modals deferred, button split, static checks only) |
| D-27 | **Farm milestones go through one reward path, keyed by milestone id (M06.4).** `FarmManager._reach(id, message)` is the only way a farm milestone happens: it records the id once ever (saved `farm.milestones`), pays the reward the reward data names for that id (`data/rewards/<id>.tres`; no rule = no reward — callers never choose an amount), opens the plots waiting on it, then announces `milestone_reached` (GameState saves, the HUD shows the card). The **milestone id is the progression hook**: plots' `unlock_on_milestone`, `MilestoneReveal.milestone_id`, reward rules and the Journal (`get_milestones()`, the registry) all name registered ids, checked statically. Milestones are reached only from game events (planting, ripening, harvesting), never from UI. Amounts unchanged (first harvest 10, all starter crops 40, starter garden 30, garden in bloom 50; others 0); points only (D-24); no save change. Exploration bonuses keep their own path until M13.1; the overall progression structure stays open (O-04) | Developer instruction (M06.4, from the plan's "one reward path") |
| D-28 | **The pond has a controlled walkable edge (closes O-07, option B; M07.3).** The pond keeps its look and position; inside its 3.6 m water a blocked core of radius 2.8 m (a `StaticBody3D` cylinder plus a matching `NavigationObstacle3D` that carves the baked navigation mesh) stops the joystick and tap-to-move, leaving a walkable shallow edge (≈ 0.45 m of water past the carve, then the bank). Chosen from the runtime audit: the pond was fully walkable by accident (the player stood on the water), while a pond solid at its full water radius left the two discoveries placed in the water (Wild Mint, River Stone) out of interaction reach. With the core, both are collected from the edge; tapping the core does nothing. No wading/swimming visuals (later art). Discoveries, the pond and the path are not moved | Developer decision (M07.3, after the runtime audit) |
| D-29 | **The follow camera never pulls in on geometry (M07.3).** The `SpringArm3D` in `FollowCamera.tscn` ignores collisions (`collision_mask = 0`), so the camera stays at its arm length everywhere. Before, the arm hit tall solids (the house, the Overlook monolith) and dropped to ~0.4–1 m, filling the screen with the player's head. Accepted trade-off: a tall object (the house roof, the monolith) can hide the player while they stand directly behind it; roof fade / cutaway is later camera polish, not part of M07.3 | Developer decision (M07.3, after the runtime audit) |
